# Duet Visual Harness

Tooling to obtain **visual evidence** of how the duet (NES) preview renderer
draws highlights in Neovim, so the diff chunking and the treesitter foreground
coloring of proposed virtual text can be iterated against real screenshots
instead of guesswork.

The immediate target is the **treesitter foreground coloring** of proposed
virtual text: today the base buffer is syntax-highlighted but the predicted
text rendered as `virt_text` / `virt_lines` is flat add-green (see
`out/func_rewrite.cage.png`). The harness exists to make that gap, and any fix,
visible.

## What it does

It renders a synthetic before/after edit straight through
`minuet.duet.preview.render` with **no model and no network**, in a real Neovim
with tokyonight + treesitter, then captures a **true-color PNG**.

Rendering the viewer (not a live prediction) is the whole point: it is
deterministic, fast, and needs no API keys. State is built the same way the test
suite does it (`package.loaded.minuet = { config = ... }`), so what you see is
exactly what the plugin would draw for that before/after pair.

## Reference images

## Files

| File | Role |
| --- | --- |
| `init.lua` | Model-free nvim driver. Loads a fixture, builds `state`, calls `preview.render`. Uses the **system nvim** (for its bundled treesitter parser set) and pulls tokyonight via `vim.pack`. Isolates nvim state under `.state/`. |
| `fixtures.lua` | Named before/after cases (incl. the diff-viewer failure cases: snake_case, camelCase, inserted-line-in-block, multi-line rewrite). |
| `shot_cage.sh` | Capture via headless wlroots (cage) + foot + grim. |
| `shot_vhs.sh` | Capture via VHS (self-contained). |
| `shot_tmux.sh` | Capture via tmux `capture-pane` + charm-freeze. |
| `flake.nix` | Capture toolchain (no neovim) + `nix run .#shot`. |

## Usage

```bash
cd experiments/duet-nes/visual-harness
nix develop -c bash shot_cage.sh func_rewrite   # -> out/func_rewrite.cage.png
# then read the PNG
```

Or via the flake app from the repo root:

```bash
nix run ./experiments/duet-nes/visual-harness#shot -- cage func_rewrite
```

Add a case to `fixtures.lua` and pass its name as the argument.

## Approaches evaluated

The task asked to try several capture strategies and report which is most
reliable. All produce a true-color PNG of the same nvim render; they differ in
fidelity, weight, and dependencies.

### 1. Headless Wayland: cage + foot + grim  (recommended default)

A single-app wlroots compositor (`cage`) runs headless with the **pixman
software renderer** (`WLR_BACKENDS=headless`, `WLR_RENDERER=pixman`) — no GPU,
which matters on this box. It launches `foot` (a Wayland-native terminal,
true color) running the nvim driver; `grim` grabs the wlr output. The inner
client exits, tearing the compositor down.

- Highest fidelity: it is a real terminal with the system's real DejaVu font via
  fontconfig, i.e. essentially how the user's wlroots/Hyprland terminal draws it.
- No GPU needed; never touches the user's visible session.
- Deps: `cage`, `foot`, `grim`.

### 2. VHS

`vhs` drives nvim in its own bundled headless terminal stack (ttyd + a headless
browser) and writes a frame via the `Screenshot` tape command. Truecolor is
preserved (nvim emits 24-bit escapes regardless of the terminal palette).

- Self-contained and portable; good when there is no wlroots stack.
- Heaviest: pulls in chromium.
- Tape gotcha: `Output`/`Screenshot` paths must be quoted.
- Deps: `vhs`.

### 3. tmux capture-pane + charm-freeze  (lightest)

nvim runs in a detached `tmux` pane; `tmux capture-pane -e -p` dumps the
rendered grid with SGR color escapes; `charm-freeze` renders that ANSI to PNG.
No compositor, no GPU, no browser.

- Truecolor survives tmux **only** with `terminal-features ",*:RGB"` set;
  otherwise tmux downsamples 24-bit to 256 colors. Verified faithful: the dump
  carries the exact duet bgs (`48;2;47;111;84` add, `48;2;154;63;85` delete).
- Renders in freeze's bundled font (JetBrains Mono), not the user's DejaVu — an
  arbitrary `--font.family` that fontconfig cannot resolve in this env yields
  blank glyphs (background fills only), so we keep the default.
- Footgun: nixpkgs `freeze` is an unrelated shellcode tool; the screenshot tool
  is `charm-freeze` (its binary is also named `freeze`).
- Deps: `tmux`, `charm-freeze`.

### Evaluated but not stood up: cua + QEMU

`cua` (`~/code/cua-repos/cua`) provides agent "eyes and hands" on a real
computer (screenshot/click/type, trajectory replay) across providers including
`docker`/`qemu-docker` (a containerized Linux desktop) and `host` (the local
machine). It is the right tool for AI-driven *interactive* GUI QA, but for
deterministic headless *highlight screenshots* it is overkill here:

- Requires `pip install cua` (a Python environment, against the repo's
  no-global-install norm) and, for the VM path, a multi-GB containerized
  Xfce/X11 desktop that is software-rendered on this GPU-less box.
- That container desktop is *less* faithful to the user's foot/kitty +
  tokyonight + DejaVu setup than cage+foot already is.
- `host` mode could screenshot the live session but is intrusive
  (non-deterministic, shows whatever is on screen) and still needs the Python
  install.

Verdict: keep it in reserve for interactive, multi-step GUI flows; the three
terminal backends above cover the screenshot need at a fraction of the cost.

## Benchmark

A subagent dogfooded the three backends (`nix develop`-driven) across two
fixtures (`word_swap`, `func_rewrite`), viewed every PNG, and ran each twice to
probe flakiness.

| Backend | First-try | Wall time | Foreground text | Stability (2 runs) | Fidelity |
| --- | --- | --- | --- | --- | --- |
| **cage** | ok | ~6s | full TS colors | byte-identical (0 px diff) | highest: real foot + DejaVu + tokyonight bg, tight 1280x720 |
| **tmux** | ok | ~7s | full TS colors | byte-identical (0 px diff) | good, but freeze's bundled font + needs cropping |
| **vhs** | failed* | n/a | n/a | n/a | n/a |

\* The benchmark caught a real bug: VHS failed in the flake devShell with `could
not open ttyd: ... ERR_CONNECTION_REFUSED`. Adding `ttyd`/`ffmpeg` did not fix it
-- the pinned nixpkgs rev's vhs/ttyd/chromium simply do not talk to each other,
while the registry rev's vhs works. Resolved by making `shot_vhs.sh`
self-contained (it invokes vhs via `nix shell nixpkgs#vhs`) and keeping vhs out
of the flake.

**Ranking (reliability = first-try + stability + simplicity):**

1. **cage** — fastest, perfectly deterministic, highest fidelity, no
   post-processing. Default.
2. **tmux** — equally deterministic, no compositor/browser, but lower fidelity
   (font) and needs trimming. Solid headless fallback.
3. **vhs** — most fragile (browser-in-the-loop, nixpkgs-rev-sensitive); kept as
   a self-contained portable option but offers no fidelity edge over cage.

**Recommendation: `cage` is the default** for iterating on highlight rendering;
`tmux` is the fallback if a wlroots stack is ever unavailable.

## Treesitter foreground coloring (the deliverable)

The harness exists to drive this work, which is implemented as a standalone,
unit-tested module plus an opt-in renderer integration:

- `lua/minuet/duet/ts_highlight.lua` -- pure module: given proposed lines + a
  language, it parses a string snapshot, resolves the `highlights` query the way
  Neovim's highlighter does (priority, then later-capture-wins), and returns
  `{ text, hl_group }` chunk lists per line. Options: `dim` (blend toward bg),
  `blend`, `bg` (the "added" tint), `base_hl`. Injected languages are followed;
  unknown languages degrade to flat `base_hl`. Tested in
  `tests/duet_ts_highlight_spec.lua`.
- `preview.lua` integration, gated by config (default off):
  `config.duet.preview.ts_highlight = true` colors proposed *blocks* and inline
  edit fragments with dimmed syntax colors over `ts_add_bg` (`ts_dim`,
  `ts_blend`, `ts_add_bg` tune it). Inline fragments are colored via
  `highlight_line_range` in the context of their full proposed line, so a word
  changed inside a string still reads as `@string` (not the `@variable` it would
  get in isolation). Covered by cases in `tests/duet_preview_spec.lua` and
  `tests/duet_ts_highlight_spec.lua`.

  Caveat surfaced by the harness: `@string` (green) over the green "added" tint
  is low-contrast (green-on-green); tune `ts_add_bg` to a more neutral tint if
  that bothers you.

Reproduce the evidence:

```bash
# A/B/C/D policy comparison (flat / full / dim / dim+tint) in one image:
MINUET_INIT=ts_demo.lua MINUET_TAG=tsdemo nix develop -c bash shot_cage.sh func_rewrite
# the integrated path through the real preview.render, flat vs ts:
MINUET_TAG=flat            nix develop -c bash shot_cage.sh block_rewrite
MINUET_TS=1 MINUET_TAG=ts  nix develop -c bash shot_cage.sh block_rewrite
```

Chosen policy: dimmed treesitter foreground + a subtle green "added" tint
(`ts_blend = 35`, `ts_add_bg = 0x294b38`), so proposed code is syntax-colored yet
still reads as "added."

## Why the system nvim, not a flake nvim

A vanilla `pkgs.neovim` would not carry the large bundled treesitter parser set
+ runtime highlight queries that the system nvim has (confirmed: `get_string_parser`
+ `query.get(lang,'highlights')` work under `-u NONE`). Since the deliverable is
treesitter foreground coloring, parser/query parity matters, so the flake ships
only the capture tools and the harness uses the system nvim. Plugins come from
nvim 0.12's built-in `vim.pack`.
